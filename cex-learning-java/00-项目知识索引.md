> **用途**：跨章节共享的"事实底座"。写/读任何一章前先看这里，避免同一结论在不同章节里说法不一致。
> **维护方式**：只增不改事实来源；结论变化时在"修订项"留一行记录，并同步受影响章节。
> **证据分级**：已证实（源码直接可见）／合理推断（符合证据但未验证）／待验证（缺关键证据）。
> **基准**：当前工作区源码，首次勘察 2026-10-25；行号仅供快速定位，以函数名为主锚点。

## 1. 一句话架构

一个 **Spring Boot 3.3 单体**（Java 21，端口 `12306`）：HTTP 接入 → 按交易对路由到**每 symbol 一个单线程 `SymbolEngine`** → 内存 `OrderBook`（跳表价格档 + FIFO 队列）撮合 → 同一请求线程内**同步**调用 `SpotAssetSettlementService` 把成交写进 PostgreSQL；身份用 Supabase JWT，充值靠三条测试网扫链，永续/跨链桥是与现货**账本隔离**的附加模块。

- 没有消息队列参与主链路（RabbitMQ 代码存在但未装配）。
- 没有 Redis / 缓存 / 分布式锁。
- 订单簿状态全部在 JVM 内存；账本状态全部在 Postgres。
- 前端 UmiJS 只负责展示与调用 REST，不参与业务规则。

## 2. 已确认的核心业务主线

### A. 下单 → 撮合 → 结算（现货，主链路）

```text
POST /api/orders
  → Supabase JWT 鉴权（SecurityConfig:36-40）
  → validateOrderPayload（MatchingController:203/229）
  → 服务端生成 clientOrderId（:113）
  → reserve 冻结（SpotAssetSettlementService:30）
  → SpotMatchingService.submit（:67）→ SymbolEngine 队列（:146）
  → TradingPairMatchingService.submit（:82）→ OrderBook.submit（:77）/ match（:200）
  → settle 结算（SpotAssetSettlementService:251）
  → OrderSubmitResponse
```

### B. 撤单 / 改单 / 查询

```text
POST /api/orders/{orderId}/cancel（MatchingController:261）
  → 校验归属 → CancelOrderCommand → OrderBook.cancel（:144）
  → settlementGateway.release（SpotMatchingService:98）→ 解冻

POST /api/orders/client/{clientOrderId}/cancel（:184）
  → 按 clientOrderId 找 open 单；找不到则直接 releaseReservation

modify（SpotMatchingService:102 → OrderBook:123）
  → cancel 旧单 + 用同一 clientOrderId 重新 submit（replaceExistingClientOrder=true）
```

### C. 链上充值 → 内部余额

```text
Scanner（EVM/Solana/Tron @Scheduled）
  → ChainDepositService.recordChainDeposit（:159）按 tx_hash upsert，≥3 确认置 CONFIRMED
  → creditConfirmedDeposit（:251）条件入账（credited_at is null）
  → user_asset_accounts.available
```

默认 `CHAIN_SCANNER_ENABLED=false`；课堂演示用 `POST /api/assets/deposits/simulate`。

### D. 永续（独立业务线，非现货撮合）

`PerpetualTradingService.submit:104` 直接按 OKX 报价成交或挂单；`processContract:308` 定时用 `bestAsk/bestBid` 触发限价单、结算资金费率、强平。**不撮合用户之间的对手单**，交易所是唯一对手方；账本在 `perpetual_*` 表，与 `user_asset_accounts` 隔离。

## 4. 状态存放位置与读写者

| 状态 | 位置 | 写者 | 读者 | 备注 |
| :--- | :--- | :--- | :--- | :--- |
| 订单（含状态、剩余量） | JVM `OrderBook.allOrders` / `openOrders` | `OrderBook.submit/cancel/modify` | 控制器查询、结算回调 | 重启全丢 |
| 幂等索引 | JVM `ordersByClientOrderKey`（key = `symbol:userId:clientOrderId`，`:323`） | `submit` 写入 | `findByClientOrder` | 只增不减 |
| 价格档 / FIFO | JVM `bids`/`asks` 跳表 + `PriceLevel` | `addOpenOrder` / `removeFromBook` / `match` | 撮合、snapshot | 重启全丢 |
| 最近成交 | JVM `recentTrades`（≤50） | `rememberTrade:144` | `GET /api/market/trades` | 重启全丢 |
| 冻结预留 | DB `spot_order_reservations` | `reserve` / `consumeFrozen` / `releaseInternal` | 结算、资产页 | `status ∈ {OPEN, RELEASED}` |
| 余额 | DB `user_asset_accounts` | 同上 + `creditAvailable` + 充值入账 | 下单冻结、资产页 | 主键 `(user_id, asset, chain, network)` |
| 成交账本 | DB `spot_asset_settlements` | `settleOrder` | 资产页流水 | 主键 `settlement_key`，只插不改 |
| 充值 | DB `chain_deposits` | `recordChainDeposit` | 资产页、入账 | 幂等键 `tx_hash` |
| 扫链游标 | DB `chain_scan_cursors` | Scanner | Scanner | 失败不推进 |
| WAL / 快照 | `./data/wal`、`./data/snapshot` | 仅测试/未接线 | 仅测试 | 运行时无文件产生 |

**三个必须记住的边界**：
1. 订单簿与订单**不在数据库**；`spot_orders`、`spot_trades` 没有任何 Java 写入方。
2. 冻结在 DB、撮合在内存，两者通过 `client_order_id` 关联，**没有跨边界事务**。
3. 结算发生在 HTTP 请求线程（`SpotMatchingService:76`），不在 `SymbolEngine` 线程内。

## 7. 链上与链下职责边界

| 能力 | 落点 | 说明 |
| :--- | :--- | :--- |
| 撮合、订单簿、成交价 | 链下内存 | 与任何链无交互 |
| 余额、冻结、结算 | 链下 Postgres | SQL 事务 + `for update` 行锁 |
| 充值收款 | 链上 → 链下扫链 | 用户转入托管地址；≥3 确认后入账 |
| 提现 | **未实现** | 无提现 Controller；仅遗留内存版 `UserAssetService.withdraw`，不被任何生产代码调用 |
| 私钥控制 | 后端 | AES-256-GCM 加密存 `hot_wallet_addresses`，前端不可读 |
| 跨链 | 链上 LayerZero OFT + 链下轮询 | 测试网演示，与撮合无调用关系 |
| 永续 | 纯链下 | 价格来自 OKX，不读链 |

资产坐标规则（`SpotAssetSettlementService.assetLocation:559`）：`SOL→SOLANA/DEVNET`、`TRX→TRON/NILE`、**其余→EVM/SEPOLIA**。因此 `BTC-USDT` 的 BTC 只是 EVM/SEPOLIA 上的一行余额——理解这一点，才不会去找"BTC 链"。

## 9. 术语表（统一口径）

| 术语 | 在本项目中的含义 |
| :--- | :--- |
| 现货（spot） | 用 quote 资产（如 USDT）直接买卖 base 资产（如 ETH），成交后立即交割；本项目唯一真正的撮合业务 |
| 撮合（matching） | 把新订单与对手盘已有挂单按价格/时间优先配对，产生成交 |
| 订单簿 / 盘口 | 买盘（bids）+ 卖盘（asks）的价格档集合；本项目用跳表维护价格档 |
| taker / maker | 主动吃单方 / 被动挂单方；成交价取 maker 价，taker 是后到的那笔 |
| 限价单 / 市价单 | 指定价格 / 不指定价格只要立即成交；REST 层把市价单固定为 IOC（`MatchingController:121`） |
| GTC / IOC / FOK / POST_ONLY | 一直有效直到撤销 / 立即成交否则取消 / 必须全部成交否则拒绝 / 只做 maker，会吃单就拒绝 |
| 冻结（reserve） | 下单时把 `available` 划到 `frozen`，防止同一笔钱被重复使用 |
| 结算（settlement） | 成交后把冻结的钱真正扣掉，并按 base/quote 交换给对手方 |
| 解冻（release） | 撤单或未成交剩余把 `frozen` 退回 `available` |
| 滑点 | 实际成交均价与预期价的差；本项目市价买用 1000 档估算来约束 |
| 幂等（idempotency） | 同一请求重复执行不产生第二笔业务效果；本项目用唯一键 + 条件更新实现 |
| WAL | Write-Ahead Log，先写日志再改内存，用于崩溃恢复；本项目有实现但未接线 |
| Outbox | 把"要发的事件"先写库再由后台投递，保证业务与消息一致；本项目只有表 |
| 托管钱包（custodial） | 交易所替用户保管私钥的地址；用户只看到站内余额 |
| 扫链 / 确认数 | 轮询链上交易并等待 N 个区块确认，防止重组回滚；本项目要求 3 确认 |
| 演示做市商 | 用系统账号按外部行情自动挂单/自成交，制造盘口深度；不消耗真实资金 |
| 逐仓保证金 / 资金费率 / 强平 | 永续概念：单仓位独立保证金 / 多空之间定期付费 / 保证金不足时强制平仓；与现货无关 |
