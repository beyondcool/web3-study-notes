## 2. 项目介绍

### 2.1 30 秒版

> 这是一个用 Spring Boot 写的**现货撮合教学系统**：HTTP 下单先冻结资金，再按交易对进入单线程队列，内存订单簿用跳表 + FIFO 完成价格优先、时间优先撮合，成交后同步把结果结算到 PostgreSQL；另外带三链测试网充值、演示做市、永续和 LayerZero 跨链桥。它刻意保留了真实交易所的边界（冻结/结算/幂等），也刻意暴露了教学取舍（订单不落库、WAL 未接线、无手续费/无 STP）。

### 2.2 2 分钟版（按"一条订单的一生"讲）

```text
POST /api/orders
  → JWT 鉴权（Supabase）
  → 参数校验 + 市价买按 1000 档估算 quote
  → reserve：插 reservation + available→frozen
  → SymbolEngine 队列（每 symbol 单线程，3s 超时）
  → OrderBook：POST_ONLY/FOK 预检 → 跳表取最优价 → 同价 FIFO 成交（maker 定价）
  → 剩余量：GTC 挂单 / IOC 与市价取消
  → settle：每笔成交给 taker 与 maker 各记一条流水，扣 frozen、加 available、退价格改善
  → 响应订单状态 + 成交笔数
```

**亮点**：单线程换确定性、条件更新防超扣、幂等键防重复记账、结算与撮合分离。
**取舍**：订单只在内存、WAL/Outbox/RabbitMQ 未装配、无手续费/STP/tick size、演示做市账本不守恒。

## 5. 十问十答（面试速查）

> 每题先给"一句话答案"，再给源码证据与一句追问准备。

**Q1：一笔订单从点击到成交，经过哪些步骤？**
一句话：鉴权 → 校验 → 市价买估 quote → 冻结 → 入 symbol 队列 → 跳表 + FIFO 撮合 → 同步结算 → 响应。
证据：`MatchingController:109` → `reserve:30` → `SymbolEngine:146` → `OrderBook:77/200` → `settle:251`。
追问准备：哪一步失败会保留冻结？（结算失败：`SpotMatchingService:76-83`）

**Q2：为什么每个交易对只用一个线程？读请求为什么也排队？**
一句话：用串行换确定性，订单簿因此完全无锁；读也入同一队列，才能读到与撮合一致的状态。
证据：`SymbolEngine:58-65`、`:88-110`（读全部 `enqueue`）、`createRuntime:177`。
追问准备：代价是什么？（读占用撮合线程；大 depth 快照是 `O(总档位数)`）

**Q3：成交价取谁的价格？部分成交怎么结算？**
一句话：取 maker 挂单价；部分成交时 maker 留在队头，taker/maker 各自扣减剩余量，结算按实际成交量。
证据：`OrderBook:229`、`PriceLevel.peek:28`、`Order.fill:101`、`OrderBook:219-222`（匹配数量）。
追问准备：限价买 3000、成交价 2990，差额去哪？（结算退回，`settleOrder:351-357`）

**Q4：下单冻结多少？市价买为什么要先估算？**
一句话：卖单冻数量、限价买冻 `价×量`、市价买按 1000 档估 quote；因为市价单没有价格，必须知道大概花多少才能冻。
证据：`reservationAmount:274-285`、`quoteForMarketBuy:244`、`MatchingController:127`。
追问准备：估不准会怎样？（实际成本超预留 → 结算抛错、冻结保留）

**Q5：结算怎么保证不重复扣钱？**
一句话：`settlement_key` 主键做幂等闸门，先插流水再改余额；重复结算在改余额前就返回。
证据：`settleOrder:303-338`、`settle:257-258`。
追问准备：一笔成交为什么结算两次？（taker 和 maker 各一条流水）

**Q6：接口超时了，订单到底有没有下成功？**
一句话：不知道。超时只取消等待（`cancel(false)`），队列里的命令仍会执行；504 表示"结果未知"。
证据：`await:194-202`、`QueuedTask.complete:302-310`。
追问准备：那怎么保证安全？（引擎层可用同 `clientOrderId` 重试；REST 目前不接收该字段）

**Q7：重启后订单和盘口为什么没了？不是有 WAL 吗？**
一句话：WAL 代码存在但没接线（`createRuntime` 用 Noop），订单只在内存，重启即丢；数据库里只剩冻结和流水。
证据：`createRuntime:177-181`、`TradingPairMatchingService:35-72`、`recoverFromWriteAheadLog:153`。
追问准备：接上 WAL 就够了吗？（不够：崩溃在 WAL 与结算之间仍会账实不一致）

**Q8：并发下怎么防止余额扣成负数？**
一句话：`update ... where available >= ?`（或 `frozen >= ?`）+ 影响行数校验，靠数据库原子条件更新，不靠应用锁。
证据：`reserve:69-90`、`consumeFrozen:396-415`、`releaseInternal:492-513`。
追问准备：为什么不用 Redis 锁？（单库事务足够；跨库/跨服务才需要）

**Q9：真实交易所必备、但这个项目没有的，有哪些？**
一句话：订单/成交落库、手续费、自成交防护（STP）、tick size/lot size、提现、风控与限频、WAL/Outbox 的实际装配。
证据：`OrderBook.match`（无 STP）、`settleOrder`（无 fee）、`validateDecimal`（无 tick）、第 08 章。
追问准备：哪一个最危险？（当前无提现，STP 只造成虚假成交量；一旦开放提现，演示做市造成的账本不守恒会变成真实资金漏洞）

**Q10：永续和跨链桥跟现货是什么关系？**
一句话：三本账互不相通。永续是独立账户、平台对赌、按 OKX 报价成交；桥直接操作链上托管钱包，不动站内余额。
证据：`perpetual_accounts`（V15）、`PerpetualTradingService:104/977`、`CrossChainBridgeService:120/291`。
追问准备：那用户永续赚的钱能提现吗？（不能，提现未实现；三本账没有互转入口）

## 6. 最容易误解的 12 个点

| # | 常见误解 | 源码事实 | 证据 |
| :-- | :--- | :--- | :--- |
| 1 | "订单会落库" | 订单只在 `OrderBook` 内存；`spot_orders` 无写入方 | `OrderBook:30-32`、第 01 章 |
| 2 | "有 WAL 就能恢复" | WAL 未接线，运行时是 Noop | `createRuntime:177` |
| 3 | "事件会发到 RabbitMQ" | 发布器未接线；即使接线也只声明 exchange、无队列/消费者 | `RabbitOrderEventPublisher:18-70` |
| 4 | "市价买一定成交" | 1000 档不够直接 400；且估价与撮合之间有竞态 | `quoteForMarketBuy:255-257` |
| 5 | "撤单一定退钱" | 撤单成功后才 `release`；解冻失败会留下冻结 | `SpotMatchingService:97-98` |
| 6 | "演示做市有资金" | 做市用户无 `users` 行/预留，结算跳过 | `OkxDemoMarketMaker:34`、`settleOrder:294-301` |
| 7 | "Solana/Tron 的 USDT 能充" | 扫描器只处理原生 SOL/TRX | `Solana:32`、`Tron:34` |

| 10 | "桥会扣站内余额" | 桥只查链上余额、直接转链上钱包 | `CrossChainBridgeService:291-345` |
| 11 | "盘口/K 线是真实用户" | 默认由演示做市每 3 秒重建并自成交 | `OkxDemoMarketMaker:168-201` |
| 12 | "模拟充值只是测试工具" | 任何登录用户都能调用它凭空加余额 | `simulateDeposit:96-157` |

## 7. 三个手推练习（10 分钟）

**练习 1：价格/时间优先**
卖盘依次挂 `100@1`（alice）、`99@1`（bob）、`99@1`（carol）；买 `101@2.5` 进来。写出三笔成交的价格、数量与剩余。
参考答案：`99@1`（bob）、`99@1`（carol）、`100@0.5`（alice 的 100 档剩 0.5）；taker 全成。对应 `OrderBookTest:106`。

**练习 2：冻结与结算**
限价买 `2 ETH @3000`，成交 `0.5 @2990` 后撤单。算最终余额变化。
参考答案：冻结 6000；成交扣 1495（2990×0.5）、退回价差 5（1500−1495）、得 0.5 ETH；剩余 4500 解冻。净：USDT −1495、ETH +0.5。对应 `settleOrder:347-357`、`releaseInternal`。

**练习 3：超时的真相**
把 `MATCHING_COMMAND_TIMEOUT_MS` 调成 1，下一笔单收到 504。此时订单一定失败吗？
